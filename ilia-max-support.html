ILIA Support Max

Support Max is an in-product AI copilot for ILIA admins. It answers ILIA & Kai-Zen questions from live documentation and data, pulls a client's documents, files bugs straight to Jira, captures product ideas, and surfaces the exact FullStory session behind an issue — all inside the ILIA screen the admin is already on. This page is the living reference for what it does and how it's maintained.

Future Feature Sets

Ideas

A running list of what's next — captured as we discuss it. Direction, not commitments.

Daily Tasks — scheduled assistant Phase 2

Standing daily jobs: check email & flag client messages, a morning digest, "agents who never logged in," recurring follow-ups, etc.

Requires: a hosted/production backend that runs on a schedule — the in-browser overlay can't run while you're away; per-admin stored tasks & standing instructions; a results surface (Tasks panel + morning digest); plus whatever each task touches (email, DB…). Stays draft-only, produces a review queue (not autonomous actions), and is logged per-admin.

Draft emails as the admin

"Send Brad his annual review" → confirm which Brad → pull the correct doc → draft into your mailbox → you review & send.

Requires: the admin connects email (one-time OAuth, scoped to create drafts); Max reads the admin's own email from their authenticated account; reuses confirm-who + pull-docs. Doc travels as a secure expiring link (preferred for PII) or an attachment. Draft-only — Max never sends; the admin does.

Email triage

Summarize the inbox, flag what matters, draft replies.

Requires: email READ access (OAuth read scope — a bigger privacy surface than drafting), with explicit consent and folder/label scoping; runs on the Daily-Tasks scheduler. Replies are draft-only.

Per-admin activity logging

Every session & action tied to the authenticated admin — full "who did what with Max" audit.

Requires: production deployment where the admin is authenticated (Max reads their Users.id/email from the session, not off the page); stamp that id on each entry via the existing audit chokepoint; decide where logs live (audit store / DB / Domo).

Agent / IMO / carrier analytics

"Which agents have the most clients," plus breakdowns by IMO / region / carrier / participant count.

Requires: the NIWD-2219 read-grant expansion — SELECT on Agents, AgentImos, Imos, AgentImoCarriers, Carriers, Participants — plus the query/tool code to join them. Everything from the Users table already works today.

Domo reporting In progress

Push Max's usage to Domo dashboards + ask Domo reporting questions in chat.

Requires: a Domo API client (client ID/secret, data scope) from Sanjay; the dataset IDs to read + an "ILIA Support Max — Activity" dataset to write; the dual-mode domo.js module (pending creds).

How It's Maintained

Where Support Max will run in production, how it's kept current, and — importantly — who can change what. "Updating" Max means different things at different layers; they're not all the same job.

🏛️ Where it runs

Today: a prototype running locally, overlaid on the live ILIA screen in the admin's browser — read-only.

In production: Max's "brain" (Claude) runs through Amazon Bedrock inside NIW's own AWS, so client data never leaves our environment and never reaches an outside AI provider. The agent's backend is hosted in NIW infrastructure, and the copilot appears inside the ILIA product.

🧩 The four layers — and how each is updated

"Training/updating" Max isn't one thing. It's four separate layers, each changed a different way:

LayerWhat it isHow it's updatedWho
KnowledgeWhat Max knows about ILIA.Reads the live ILIA Confluence space (auto-refreshes). Edit the docs → Max knows it. No deploy.Anyone who edits Confluence (indirect)
Behavior & guardrailsHow Max acts — its persona, rules, "stay in its lane," what it will and won't do.An owner-controlled configuration. This is the "training" that shapes its behavior.Owner (Jamin) only
CapabilitiesWhat Max can do — the tools (pull docs, analytics, file bugs).A code change, shipped by a deploy. Changes only via another deploy.Devs build & deploy
Deployment & infraRunning the code — Bedrock, hosting, connections.Standard deploy / infra setup.Devs / infra (Mohit)

❓ "Where was that updated?" (e.g. better DB handling, pull-docs)

Improvements like handling the ILIA DB better or adding the pull-docs feature are capability (code) changes — made in Max's codebase and shipped by a deploy. Once live, they change only with another deploy.

Teaching Max new ILIA facts is different — that's just updating the Confluence docs. Max reads them live, so no deploy is needed; it picks the change up on its own.

🔐 Who can change how Max thinks

By design, only the owner controls Max's behavior and guardrails. Changes to how it thinks, what it's allowed to do, and how it responds go through the owner — not ad-hoc, and not by devs. Devs deploy the code; they don't retrain or redirect it. (Enforced by keeping the behavior configuration owner-owned and change-controlled.)

Owner (Jamin)Controls behavior, guardrails, and what knowledge Max draws on. The only one who changes how it thinks/acts.
DevelopersBuild & deploy new capabilities and fixes. They ship code — they don't change its behavior/training.
The team (via Confluence)Keeping ILIA's docs current automatically keeps Max's knowledge current — read-only, no deploy.
