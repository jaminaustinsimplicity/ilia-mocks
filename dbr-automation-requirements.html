DBR Automation Requirements

Automating the Death Benefit Reduction (DBR) process for Kai-Zen IUL policies in Policy Years 11–15 (early cohorts start Year 10). Today it's run manually by ops; this project makes ILIA proactively detect eligible policies, notify clients on a schedule, collect their election — the client picks one of 3 ready illustrations (Full / Half / No reduction) via DocuSign — and let Marissa manage every case from Tranche Management. This page is the living requirements — built event by event.

DBR Trigger

How ILIA knows when to send: it scans daily for eligible Kai-Zen policies approaching their DBR deadline (window starts Yr 10 or 11 by cohort, through Yr 15), then auto-sends the DBR notice on a set schedule — no manual kickoff.

Before the notice — carrier illustration request new · Sep 17

Around year 11 (some cohorts year 10), before the client notices go out, we request the in-force illustrations from the carrier. The email asks the carrier to run the reduction 3 ways (Full / Half / No) with the low points, and states the 50% rule + which amount comes off the term rider vs. the base.

  • →Carrier emails the illustrations to an AWS landing spot (Mohit setting up) — sent where they go today, copied to AWS
  • →Ben's scraper reads them from AWS, validates, and populates the 3 choices + the in-force rate onto the election form & writes the fields to Case Details
  • →6 illustrations per client: 3 reduction (Full / Half / No at the in-force rate) + 3 low points — run separately at 0% / guaranteed (Paul: low point ≠ in-force illustration)

⏳ Allianz in-force illustrations can take ~3 weeks — request early. Judy to check with Marissa so carrier emails aren't duplicated.

Reduction rules new · Sep 17
  • 50% max rule: a reduction can never exceed 50% of the current death benefit (from the carrier feed). Max reduction = current DB ÷ 2.
  • Term rider first: always reduce the term rider before the base policy (~90% of cases have a term rider). No term rider → reduce from base; the 50% cap still applies.
  • Example: Yr 11 planned DBR 500K = 400K term + 100K base. Half = 250K, all from the term rider.

Core principle — one record, one status
  • A client's DBR lives on their case, per policy year. Its DBR Status is the single shared value.
  • Both screens are windows onto the same record — nothing is copied between them; they stay in sync because they read & write the same data.
  • Every field & action has exactly one home — no double entry, no conflicting edits.
