Open item AC now has to write into ILIA

Moving the flow inside AC removes the hand-off the agent used to feel — and moves the work onto AC. Because the agent never reaches niwcorp, AC has to post the completed registration into ILIA itself: the Rep Sheet details, the resolved IMO, the carriers, and the certification result.

The good news is the endpoint already exists — it is the same one niwcorp.com posts to today, and it needs no ILIA change. The ask on NIW is narrow: agree the payload, and decide where the certification result is recorded, since there is no field for it on the agent record right now. The mapping is in the tech note under Agg structure.

The aggregator is never in the payload. The registration API accepts IMOs only — the aggregator is read from that IMO’s aggregatorId. That is the schema reason the agent never picks an aggregator: send the right IMO and the roll-up resolves itself.
The LPL flag has nowhere to live on the agent record. Agent has no external-id, NPN, licence or affiliation column. Cheapest path: don’t store the flag — use it to pick the right LPL institution IMO (or LPL Independent) at registration, and the aggregator is implied. Storing it needs a schema change on NIW’s side.
Email is the only join key. There is no Salesforce ID, NPN or external ID on the ILIA agent record, and email is enforced unique across all users. If AC sends an email that differs from an existing ILIA record, the registration either collides or creates a second person — this is what the pre-population note on the registration screen is protecting against.
Registration writes five records, not one. One call creates the Cognito user, User, Agent, AgentImo (+ AgentImoCarrier) and AgentRegistrationRequest at status PENDING, then alerts every active admin. So a bad payload is a partial agent, not a failed form.

ILIA column verified against niw-api — public-api/agent/request + the User / Agent / AgentImo / AgentRegistrationRequest models. AC column: unverified, needs the Agent Center team.

LPL becomes an Aggregator account — ILIA’s hierarchy level that sits above IMOs and exists precisely so a parent organisation can see the business written beneath it. Every LPL-affiliated institution becomes its own IMO account underneath. Independent agents get an IMO account of their own, LPL Independent, so they have somewhere to live.

Existing entity, set up as an ILIA account Net-new container we create Repeats per additional firm

Both agent types reach the same place by different routes, and both roll up to LPL. The dashed teal path is what LPL actually gets out of being an aggregator: read-only visibility of every enrolment written beneath it, per institution or across all of them.

Why it sits in this plan The Rep Sheet decides where the agent lands

The Tech notes on the registration screen call for AC to tell NIW whether the agent is tied in with LPL. This structure is why that flag matters: it determines which IMO account the new agent is placed under — their own institution, or LPL Independent if they’re direct.

Get the flag at registration and the agent lands in the right place first time, and LPL’s roll-up reporting is correct from day one. Miss it and someone re-parents the agent by hand later, which is exactly the kind of clean-up the aggregator model exists to avoid.
