What this email must cover

  • Who the giftor is — name and email, so the agent has a record of exactly who was invited.
  • Loved ones, if any were added — count and names when the agent added them during the invitation; an explicit “none — the giftor will add their own” when they didn’t.
  • Who actually invites the loved ones — short, plain copy making clear the giftor confirms details and sends the invitations from their own portal, after creating their ILIA account.
  • Where to track it — a note that giftor invitations and participants are managed in the Giftor Portal inside the ILIA agent portal.
  • One CTA — a button that deep-links straight to the Giftor Portal screen.

2026 is a generational window for gifting

Federal gift and estate exemptions are at historic highs, and the scheduled cut that was going to halve them has been removed. That makes funding a Kai-Zen policy for a child or grandchild materially easier to do inside the limits.

Design & dev notes
Structure
  • Nav placement. “Giftor Portal” sits directly under Client Management and above Agent Links. The NEW pill is a launch affordance, not permanent.
  • One collapsed card per giftor. Collapsed shows the high-level detail an agent scans for: giftor name and email, giftor status, number of loved ones, and last activity. Expanding opens the loved ones section belonging to that giftor.
  • Loved ones live inside the giftor. There is no flat list of loved ones across giftors — a loved one only exists in the context of the giftor gifting to them.
  • Agent functions in the expanded section: add a loved one, run and re-run illustrations, view an illustration, edit details, and see each loved one’s status. Enrollment links appear once a loved one is enrolling.
  • Kai-Zen policy indicator. Each card shows, right beside the giftor’s name, whether they already hold a Kai-Zen policy — ilia knows this at invitation time and it is the single most useful fact about a giftor at a glance. Placed inline with the name rather than in its own column so it reads as an attribute of the person, not as another status to scan.
  • The policy flag says nothing about Client Management. Every client user appears in Client Management — giftors, ordinary Kai-Zen clients, and loved ones alike. So holding a Kai-Zen policy is not what puts someone in that list, and an earlier draft that implied otherwise was wrong and has been removed. The badge answers one narrow question: does this giftor hold their own Kai-Zen policy? That matters for auto-populating the existing policy (NIWD-1871) and for what financial data can be shared across (NIWD-2264) — not for where the person can be found.
  • This screen is a lens, not the only home. Because everyone is in Client Management, the Giftor Portal is a GWT-specific view over people who also appear there — not a separate universe. It should complement Client Management rather than compete with it: an agent who lands here should be able to reach the same person’s full client record, and vice versa.
The shared, living section
  • Both the agent and the giftor work in the same data. The giftor sees these same loved ones in their giftor portal and can add to or change them. Either party can run an illustration, at the same time or at different times, so a loved one’s data can change out from under whoever is looking at it.
  • Every change is attributed. Each illustration shows who ran it and when, with giftor-made changes picked out in a distinct colour, so an agent can immediately see that the giftor has been in and changed something.
  • Illustrations are versioned (“Ready · v2”) rather than silently replaced, so there is a history when the two parties disagree.
  • Concurrent access is surfaced and acted on. When ilia detects the giftor inside a loved one’s details while the agent is in the same record, authority goes to the giftor: the agent’s edit controls for that loved one are disabled, the row is visibly locked, and the banner names who is in and why. Read-only actions (View illustration) stay available. This is the agent-facing half of NIWD-2260.
  • The lock is per loved one, not per section. Only the record the giftor is actually inside is locked — the agent can carry on with every other loved one under that giftor. A whole-section lock would punish the agent for the giftor opening one row.
Who can do what
  • Only the giftor can send an invitation to a loved one. The agent has no Send control anywhere in this screen — deliberately. The agent prepares; the giftor signs off and sends; NIW admin approves. The green panel states this in plain language, and the agent’s only nudge is “Remind [giftor]”.
  • The giftor is the final sign-off on illustrations. Loved ones the agent has prepared sit at Awaiting giftor until she reviews and sends.
Open questions
  • Conflict resolution — simultaneous: ANSWERED. If both are in the same loved one at once, the giftor wins and the agent is locked out of that record (above). Still open: the sequential case. If the agent edits at 10am and the giftor edits at 2pm, nothing is simultaneous and no lock fires — so is it simply last-write-wins? Versioning makes the history visible but does not decide the winner.
  • Lock mechanics (open). What counts as “inside the details” — an open modal, an in-progress edit, or an active session? And how does the lock release if the giftor closes their laptop mid-edit? A stale lock that never clears would block the agent indefinitely, so it needs a timeout. Worth settling alongside NIWD-2260, since the enrollment session lock presumably already answers this.
  • Re-confirmation after a late change. If the giftor has already confirmed a loved one and the agent then re-runs the illustration, does that reset the loved one to unconfirmed? It probably must — otherwise the giftor signs off on figures that later changed.
  • Editing after invitations have gone out. Card 3 shows loved ones already enrolling. How much can an agent change at that point, and does a change force the loved one to re-confirm?
  • Session lock (NIWD-2260) and admin edit rights (NIWD-2262) both land squarely on this screen. The live banner assumes we detect concurrent access; if the eventual lock is hard rather than advisory, the agent may be blocked from editing entirely while the giftor is in.
  • Visibility scope. Only giftors invited by this agent, or everything under their agency / IMO?
  • Who gets the menu item — all agents, or only GWT-approved (Preferred) agents?
  • Cross-navigation between here and Client Management (open). Settled: all client users — giftors, ordinary Kai-Zen clients and loved ones — appear in Client Management. What is not settled is how the two surfaces link. Does a giftor row here deep-link to their client record, and does a client record show that this person is a GWT giftor with n loved ones? Without that, an agent has two lists of the same people and no thread between them.
  • Source of truth for the Kai-Zen policy flag (open). The agent answers “Does the Giftor currently have a Kai-Zen policy?” during the invitation, but the agent can be wrong or simply not know. The indicator on the card should be driven by ilia’s own policy record (the same lookup behind NIWD-1871’s auto-populate), with the agent’s answer treated as a hint at invite time only. Worth confirming which one wins when they disagree.
  • Loved ones as clients — ANSWERED. Loved ones are client users like any other and do appear in Client Management in their own right. So an agent will see the same loved one in two places: here, nested under the giftor gifting to them, and there, as a standalone client. That is by design, not duplication — the two views answer different questions. Worth making sure a loved one’s client record shows who their giftor is, so the relationship is not lost when they are viewed standalone.
  • Status vocabulary. The chips here are indicative. Align them with the three-track Account / Enrollment / Policy model before build rather than inventing a fourth set.
Build note
  • Not a component spec. Layout, behaviour and copy are the point. Build with ILIA’s existing agent-portal components, nav patterns, table and empty-state styling rather than reproducing this markup. Terminology is “loved ones”, not “recipients”, per NIWD-2455.
